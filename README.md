# ReplyRight

**Say it better. Be yourself.**

ReplyRight is a dating communication companion for iPhone. Share a conversation, say what you want your reply to do, and get three natural, different ways to say it, in your own voice. It comes with a custom keyboard, a share extension, a conversation coach, and a strict privacy model.

This repository contains the native iOS app and the API backend it talks to.

```
backend/                       Next.js, API only (the AI lives here; the app holds no AI keys)
ios/
  ReplyRight.xcodeproj         Open this in Xcode
  ReplyRight/                  SwiftUI app
  ReplyRightKeyboard/          Custom keyboard extension (UIKit)
  ReplyRightShare/             Share extension
  ReplyRightUITests/           UI tests
  Packages/ReplyRightKit/      Shared Swift package: ReplyRightCore + ReplyRightUI, with unit tests
  Config/*.xcconfig            Bundle identifiers, App Group, backend address
  ReplyRight.storekit          Local StoreKit test products
  scripts/                     Project generator and checks
docs/                          Architecture, design system, privacy model
```

## Status: read this first

The backend was built, run and tested in the environment where this was written. **The iOS code was not compiled or run there**, because that environment was Linux with no Xcode, no simulator and no Swift toolchain. Concretely:

| Part | State |
| --- | --- |
| Backend API | Type-checked, linted, production build passes, 51 automated tests pass, exercised over HTTP in demo mode |
| Real AI output | **Not exercised.** No Anthropic API key was available. Demo mode and all plumbing were |
| Model comparison eval | Harness written, graders unit-tested, dry-run only. **Not run against live models** |
| Swift sources (53 files, about 13,300 lines) | Parse cleanly with a tree-sitter syntax check. **Never compiled** |
| Xcode project | Generated by script and verified structurally with an independent parser. **Never opened in Xcode** |
| Unit tests (87) and UI tests (3) | Written. **Never run** |
| Review | The shared package had a full independent read-through (no compile errors found, four runtime issues fixed). The app and both extensions had the author's own review plus scripted cross-checks (every design token, model member and argument label at 290 call sites resolves). Independent reviews of those targets were started but did not finish |

Expect to fix some compile errors on first build. The code was written conservatively against iOS 17 APIs to keep that list short, but an uncompiled codebase of this size will have some. Budget time for it before anything else.

## Requirements

- macOS with **Xcode 16 or later** (the code relies on SwiftUI's `View` being main-actor isolated, which arrived with the iOS 18 SDK)
- **iOS 17.0** minimum deployment target, iPhone only
- Node.js 20.9 or later for the backend
- An Apple Developer account for running on a device, App Groups, and subscriptions
- An Anthropic API key for real replies (optional: without one the backend runs in a clearly labelled demo mode)

## 1. Run the backend

```bash
cd backend
npm install
cp .env.example .env.local      # optional: add ANTHROPIC_API_KEY for real replies
npm run dev                     # http://localhost:3000
```

Check it:

```bash
curl http://localhost:3000/api/v1/status
curl -H 'content-type: application/json' \
  -d '{"conversation":"Them: are we still on for friday?","intent":"flirt"}' \
  http://localhost:3000/api/v1/replies
```

Other commands: `npm test` (51 tests), `npm run typecheck`, `npm run lint`, `npm run build`.

### Environment variables

All of these stay on the server. Full comments are in `backend/.env.example`.

| Variable | Default | Purpose |
| --- | --- | --- |
| `ANTHROPIC_API_KEY` | none | Enables real AI. Without it the API returns labelled samples (`"mode": "demo"`) |
| `AI_PROVIDER` | inferred | `anthropic` or `demo` |
| `AI_MODEL` | `claude-opus-5-5` | Model for every task |
| `AI_MODEL_ANALYZE`, `_REPLIES`, `_REFINE`, `_COACH` | `AI_MODEL` | Per-task model overrides |
| `AI_EFFORT`, `AI_EFFORT_<TASK>` | analyze low, replies medium, refine low, coach medium | Reasoning effort |
| `FREE_DAILY_GENERATIONS` / `FREE_DAILY_COACH_MESSAGES` | 10 / 3 | Free plan daily limits |
| `PRO_DAILY_GENERATIONS` / `PRO_DAILY_COACH_MESSAGES` | 400 / 200 | Pro fair-use ceilings |
| `FREE_INTENTS` | natural, flirt, laugh, interest, keep_going, boundary | Intents on the free plan |
| `USAGE_LIMITS` | on | `off` disables daily limits for local work |
| `RATE_LIMIT_PER_MINUTE` | 30 | Per-IP request limit |
| `APPLE_BUNDLE_ID` | `com.replyright.app` | Signed transactions for any other app are refused |
| `PRO_PRODUCT_IDS` | the two Pro products | Product ids that grant Pro |
| `ENTITLEMENT_ALLOW_SANDBOX` | true | Accept sandbox purchases (TestFlight and App Review use them) |
| `ENTITLEMENT_TRUST_XCODE` | false | **Development only.** Accept purchases made with Xcode's local StoreKit testing |
| `NEXT_PUBLIC_SUPPORT_EMAIL` | placeholder | Shown on the support page |

### Choosing the production model

The model is configurable per task so you can trade naturalness, latency and cost without a code change. `backend/evals` holds a comparison harness (18 hand-written cases covering tone, voice, Spanish, starters, boundaries, manipulation requests, a minor signal and prompt injection):

```bash
npm run eval -- --dry-run     # plan and cost estimate, no API calls
npm run eval -- --models claude-opus-5-5,claude-sonnet-5-5,claude-haiku-5-5 --reps 2 --yes
```

It makes billed API calls and has not been run yet, so the default model is a starting point, not a measured choice. See `backend/evals/README.md`.

## 2. Open the app in Xcode

```bash
open ios/ReplyRight.xcodeproj
```

1. Xcode resolves the local package `Packages/ReplyRightKit` on its own.
2. Select the **ReplyRight** scheme and an iPhone simulator, then Run.
3. The first build is the moment of truth described under Status. Fix what the compiler reports.

If Xcode will not open the project, regenerate it. Either `python3 ios/scripts/generate_xcodeproj.py` (the script that wrote it), or `brew install xcodegen && cd ios && xcodegen generate` (from `ios/project.yml`).

**After adding, moving or deleting Swift files, run `python3 ios/scripts/generate_xcodeproj.py` again** (or add them in Xcode as usual; the script is only needed if you want the project regenerated from disk).

### Identifiers to make your own

Everything is set in one place, `ios/Config/Shared.xcconfig`:

| Setting | Default | Notes |
| --- | --- | --- |
| `RR_BUNDLE_ID_PREFIX` | `com.replyright` | Bundle ids become `<prefix>.app`, `<prefix>.app.keyboard` and `<prefix>.app.share` |
| `RR_APP_GROUP` | `group.com.replyright.shared` | Register this App Group in your developer account |
| `DEVELOPMENT_TEAM` | empty | Your Team ID. Empty is fine for the simulator |

Keep the backend's `APPLE_BUNDLE_ID` equal to the app's bundle identifier.

## 3. Run on the simulator

1. Start the backend (`npm run dev`). Debug builds talk to `http://localhost:3000`, which the simulator can reach.
2. Run the **ReplyRight** scheme.
3. Go through onboarding, then try Home, Paste a message, Read the conversation, Write my replies.

Without an API key every result is marked as a demo sample. That is expected.

To try the keyboard on the simulator: Settings, General, Keyboard, Keyboards, Add New Keyboard, ReplyRight. Then tap ReplyRight in the list and turn on Allow Full Access for the AI features.

## 4. Run on a physical iPhone

1. Set `DEVELOPMENT_TEAM` in `ios/Config/Shared.xcconfig`, and change `RR_BUNDLE_ID_PREFIX` to something you own.
2. In Xcode, for each of the three targets, open Signing & Capabilities and confirm the App Group is listed and has no errors. Automatic signing registers it.
3. Point the app at your Mac. Either edit `RR_API_HOST` in `ios/Config/Debug.xcconfig` to your Mac's network name (for example `my-mac.local:3000`), or run the app and set the address under **You, Developer** (debug builds only). The phone and the Mac must be on the same network, and iOS will ask for local network permission.
4. Run the backend so it listens on the network: `npm run dev -- --hostname 0.0.0.0`.

## 5. Enable the ReplyRight keyboard

On the iPhone: **Settings, General, Keyboard, Keyboards, Add New Keyboard, ReplyRight.** The app's keyboard guide (You, ReplyRight keyboard) has a button that opens the right Settings page.

- **Typing works straight away**, with no extra permission.
- **AI features need Allow Full Access.** iOS requires Full Access for any keyboard that uses the network. With it on, the keyboard still sends nothing while you type. It sends text only when you tap Reply or Rewrite, and only that draft plus any conversation you chose to hand over.
- **AI switches itself off** in password, one-time-code, payment and number-pad fields.

What a keyboard can and cannot do, honestly: iOS shows a keyboard only the text field being typed in. It cannot read the conversation above it in WhatsApp, Instagram, Tinder or Messages, and ReplyRight does not pretend to. To get replies that fit a chat, the user gives the keyboard the conversation in one of three ways: copy a message and tap "Use copied message" in the keyboard; share a screenshot or text to ReplyRight and choose "Send to my keyboard"; or tap "Use this chat in my keyboard" after getting replies in the app.

## 6. Test subscriptions

Products are defined in `ios/ReplyRight.storekit` and wired into the shared scheme, so purchases work in the simulator with no App Store Connect setup.

| Product | Identifier | Test price |
| --- | --- | --- |
| Pro Yearly | `com.replyright.pro.annual` | 39.99 |
| Pro Monthly | `com.replyright.pro.monthly` | 6.99 |

Prices are product hypotheses. The app never hardcodes one: it shows whatever StoreKit returns, including the computed yearly saving.

1. Run the app from Xcode, open **You, See ReplyRight Pro**, and buy a plan. Use **Debug, StoreKit, Manage Transactions** in Xcode to expire, refund or renew it.
2. Start the backend with `ENTITLEMENT_TRUST_XCODE=true`. Purchases made through Xcode's local testing are not signed by Apple, so the server refuses them unless told otherwise. Without this flag the app shows Pro, the server still applies free limits, and the app tells you the subscription has not been confirmed yet.
3. For real verification, use a sandbox Apple Account on a device with products created in App Store Connect. The server then verifies Apple's signature chain itself.

How entitlement works: the app derives Pro from transactions StoreKit has verified on the device, and forwards the signed transaction to the backend with each request. The backend verifies the certificate chain against Apple Root CA G3, the signature, the bundle id, the product, expiry and revocation. A client-side "I am Pro" flag is never trusted. If the StoreKit file does not load in your Xcode version, recreate it with File, New, StoreKit Configuration File, using the identifiers above.


## 8. Prepare an App Store release

1. **Deploy the backend** over HTTPS and set `RR_API_HOST` in `ios/Config/Release.xcconfig`. Set `ANTHROPIC_API_KEY`, `APPLE_BUNDLE_ID` and `PRO_PRODUCT_IDS`. Leave `ENTITLEMENT_TRUST_XCODE` off.
2. **Replace the in-memory stores** before running more than one server instance. The rate limiter and daily usage counters are per process (`backend/src/lib/server/rate-limit.ts`, `usage.ts`); both have an interface ready for a shared store.
3. **Create the products** in App Store Connect with the identifiers above, in one subscription group, with the yearly plan ranked above the monthly one.
4. **Legal pages.** `backend/src/app/privacy`, `terms` and `support` describe how the software behaves. They are drafts and say so. Have them reviewed by a lawyer, add your company details, and set the support email.
5. **App Privacy answers.** The privacy manifests declare: user content (the conversations sent for processing), a random install identifier, and purchase history, all for app functionality, none linked to identity, no tracking.
6. **Age rating.** The app is for adults and has an 18+ confirmation in onboarding. Rate it accordingly.
7. **Review notes.** Explain that Full Access is optional and used only for network requests the user starts, and that the keyboard works without it. Demo mode must be off for review: reviewers need real replies.
8. **Archive** with the Release configuration, validate, and upload.

Known gaps to close before launch are listed in `docs/ARCHITECTURE.md`.
